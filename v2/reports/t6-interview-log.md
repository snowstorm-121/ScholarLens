# T6 指标与运行器：实施及面试复盘

日期：2026-10-15。状态：工程与机器验收完成，用户手算理解待核对。

范围：固定官方评分器、实现 span 覆盖指标和共享运行器，仅运行 5 道 train 小样例。
不运行 T7 Dev 对照、T8 Test；不提交或推送 Git。用户手算理解不能由机器测试代替。

## 已确认的设计陷阱（不是虚构运行故障）

### 官方空证据评分可能掩盖调用失败

- 来源：官方 `paragraph_f1_score` 在预测和参考 evidence 都为空时返回 1。
- 风险：无答案题的模型连接失败若被适配成空 evidence，会错误获得满分。
- 处理：真正缺失/失败的预测传给官方 scorer 时保持“预测不存在”，其 Answer/Evidence F1 均为 0；仍保留在总分母中。
- 验证：无答案正确拒答为 1/1；缺失、异常、未闭合 thinking 等受控样例为 0/0，单列系统错误。
- 面试要点：使用官方 evaluator 也必须核对输入适配，不能拿服务故障刷拒答和证据分数。

### 片段里提到一段证据，不等于整段被模型看到

- 风险：chunk 与 gold 段落只要重叠就算命中，会夸大召回；将引用扩展回整段算官方 Evidence F1，也容易冒充真实 context。
- 处理：按 paper_id/paragraph_id 合并实际字符区间，完整覆盖才算段落命中；另报实际 context 覆盖。官方 Evidence F1 的输入明确是有效引用所对应的原始整段，不声称模型看到了整段。
- 验证：半段不命中、两个有 overlap 块合并能覆盖、有一字符缺口不能覆盖；不同参考组不混搭凑完整组。
- 面试要点：来源映射、官方段落匹配和实际上下文覆盖是不同指标。

### MRR@10 与生成 Top-5 的深度不同

- 风险：直接拿 QA Top-5 计算 MRR@10，看似字段齐全，实际没有检查第 6–10 名。
- 处理：用 UI 相同 retriever 一次取 Top-10，真实 QA 只回放其中 Top-5 前缀，不另写排序器。audit 保留 QA 原始五条检索输入，评测另存 metric_retrieval_results。
- 验证：运行器测试检查只检索一次、QA 使用该排名的前缀；MRR 定义仍为首次完整覆盖任意 gold 段落，而不是完整证据组。
- 面试要点：指标深度和生成预算不能相互替代，更不能让评测悄悄用更强检索。

## 实际发现并修复的问题

### 1. QA 已截掉 thinking 开头，清洗 answer 字段仍会给推理文本打分

- 现象：原始输出为 `<think>FINAL ANSWER\nresult`，上游解析后 answer 只剩 result；仅清洗 answer 时，gold=result 的 Answer F1 得到 1。
- 定位：推理标记在 QA 协议分割阶段丢失了，评分阶段已无法从短 answer 判断来源。
- 复现：回归测试在修复前得到 1 而预期 0。
- 修复：优先从完整 raw_output 清除完整/未闭合 thinking，再提取 FINAL ANSWER；引用编号也从同一份清洗后的最终正文提取。无原始输出的系统合成拒答才退回 answer。
- 验证：增加真实解析边界等案例，指标测试从 12 项扩到 18 项通过。
- 面试要点：数据经过上游转换可能丢失判错所需信息，评分要保留并使用原始输出。

### 2. 不覆盖首次结果，却可能把半截 JSON 永久留下

- 现象：直接以 x 模式打开最终文件再 json.dump，遇不可序列化对象时文件已创建；续跑见文件存在会跳过，复算无法解析。
- 定位：独占创建防覆盖，不等于完整内容原子发布。
- 复现：测试序列化异常后断言文件不存在，修复前失败。
- 修复：先在内存序列化，再同目录临时文件写入、flush/fsync，最后 hard link 不覆盖发布；异常清理仅本次临时文件。实验文件锁限制单写者。
- 验证：序列化失败、发布前受控中断、首次内容不可覆盖均测试通过；Markdown 可在 summary JSON 已存在时补齐。
- 边界：这是本地同一文件系统的原子可见性保护，不宣称解决所有文件系统或硬件损坏；进程强杀可能留下不可见的临时文件，但不被当作完成结果。
- 面试要点：幂等、原子性和不覆盖是三个不同保证。

### 3. 续跑只比配置和代码，运行时变化仍可能混入同一批

- 现象：Ollama runtime 从 original 改成 changed 的测试，早期 resume 没有拒绝。
- 原因：环境信息只保存，不进入续跑契约；余下问题可能换了运行环境却沿用旧标记。
- 复现：预期抛错的测试修复前失败。
- 修复：Python、平台、实际 Ollama 服务版本、关键包版本纳入契约，续跑重新采集并比对；不一致要求新 experiment。
- 验证：改配置、代码指纹或运行时都不能接着写旧实验；相同契约不重跑已有答案。
- 面试要点：保存 provenance 不够，还要在续跑时执行一致性约束。

### 4. 官方源码快照多一个末尾空行；网络失败不能当校验成功

- 现象：用补丁保存源码时末尾多一个换行；再次访问 raw 域名偶发 TLS 失败。管道若只看最后 shasum 的成功，会得到空内容的哈希而误判下载正常。
- 处理：没有信任这次校验，改读固定提交 GitHub contents API 的对象 SHA/字节数，与本地 git hash-object 比对；校正尾部空行。
- 验证：文件为 6,345 字节，Git blob `daa0e48d32c55e6cd23d21e0d6254a35bc359ae4` 与官方一致；SHA-256 `781aba7cd8e524bef4f0a1b4bf3504e5b02cb1d8d5bf32a8f0a89dfa83e86bfe`。
- 面试要点：固定 commit 和本地哈希之后，还应确认快照字节确实来自该固定源，不能只把自己文件的哈希写进配置。

### 5. 第一次 train 烟测暴露截断和拒答，不挑题粉饰结果

- 固定抽取 3 道可回答、2 道无答案 train 题，按 seed=42 的问题哈希排序，预测前确定，不看成功率挑题。
- 初次生成：2 道可回答题拒答、1 道到 512 token 输出上限而 error/output_truncated；2 道无答案规范拒答。检索 Top-5 没有完整覆盖三道可回答题的 gold 段落。
- 处理：保留首次全部记录；不增加输出上限、不重写问题、不换容易题。由于本轮随后修复评分/持久化缺陷，初版 smoke 单独标记为 superseded，最终用相同五题、新代码形成新批次，不称质量优化。
- 原始记录：`artifacts/evaluation/t6-train-{retrieval,generation}-first/`，版本说明 `artifacts/t6/initial-smoke-status.json`。
- 面试要点：测试通过证明实现按约定计分，不证明检索/生成质量高；小样例失败是后续有界 Dev 实验的输入，不能倒改规则。

### 6. CLI 建检索器却渲染整页，隐式联网抓更新日志

- 现象：真实检索烟测日志出现对 GitHub releases 的 TLS 失败，不是本机 Nomic 调用失败。
- 定位：application_retriever 调用 App.make，后者会渲染 HelpPage；该页面主动下载 changelog。源码确认 BaseApp.__init__ 已完成索引和设置初始化。
- 复现：将 make 设为禁止批处理渲染的断言，调用共同 factory，旧实现触发断言失败。
- 初次修复只删除 make，实际五题却全部报 `NoneType.get_selected_ids`：索引虽然初始化，selector 之前依赖 Chat 页面渲染才创建；原测试替换了整个 get_retriever_pipelines，漏掉这个真实依赖。
- 完整修复：不渲染整页，但先调用注册索引的 get_selector_component_ui，再用同一个 get_retriever_pipelines。只构造本地选择控件，不触发 Help；UI 页面构建流程保持原样。
- 验证：改进回归保留真实 FileIndex.get_retriever_pipelines 和 FileSelector.get_selected_ids，先复现 None 错误，再确认显式 selector 初始化通过；实际五题另开新批次验收，不改旧失败文件。
- 边界：修复的是批处理的冗余渲染；不宣称对上游所有模块做了网络隔离审计。上游 NLTK 导入的缓存检查提示仍保留，不隐藏。
- 面试要点：复用同一 pipeline 不等于批处理必须加载和渲染所有 UI 副作用。
- 补充要点：Mock 太宽会遮住生命周期依赖；报错批次也留在 `*-accepted` 目录，目录名不代表验收成功，是否有效以最终报告和版本说明为准。

### 7. 生成失败曾把成功的上游召回也抹成零

- 现象：单独检索的 MRR@10 为 0.05556，而相同五题生成批次变成 0；逐题确认唯一第 6 名证据命中的问题恰好生成截断。
- 原因：早期 score_question 用总 status=error 将检索和 context 都替换为空，混淆了出错阶段。
- 复现：构造完整召回、context 已覆盖、但生成 output_truncated 的测试，原实现覆盖指标为 0，预期 1。
- 修复：检索和实际 context 的指标只依据实际存在的块；缺失时才是空。生成失败的 Answer/Evidence F1 仍为 0，系统错误仍计数、分母不缩小。
- 验证：对应反例通过，同一五题新版本再验收；此前 final 批次保留为旧评分实现，不选取最好输出。最终有效批次为 `t6-train-{retrieval,generation}-v2-final`。
- 面试要点：失败要定位到阶段；保留失败分母不等于把所有已成功阶段一并改写成失败。

## 最终结果怎么诚实讲

最终五题与首次五题相同，模型配置不变；最终仍是两道无答案正确拒答、两道可回答拒答、一道截断。
独立检索及生成中保留的上游 MRR@10 均为 0.05556，Top-5 完整段落覆盖为 0；
官方 Answer/Evidence F1=0.4 只来自无答案题得分，不是可回答题表现好。
没有成功的非拒答输出，引用指标是 N/A，不写“100% 引用可追溯”。

可练习的表达：

> 我给论文问答应用补了可复算评测链路，直接使用固定版本官方 F1，再单独衡量完整段落召回和实际 context 覆盖。
> 实现时发现原始 thinking 丢失会污染评分、实验中断会留下半文件、生成错误会错误抹掉检索结果，分别用反例复现并修复。
> 五题 train smoke 的质量并不好，仍有证据不足与截断；这一步证明的是计分和审计正确，不是证明系统质量达标。下一步才做预定的 Dev 对照。
